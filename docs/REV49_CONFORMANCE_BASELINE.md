# rev49 — normative 3.0 conformance baseline (P0–P3)

## Scope and status

This revision installs the user-supplied `SHALIMAR_LANGUAGE(1).md` as `docs/SHALIMAR_LANGUAGE.md`, adds executable conformance gates and corrects one real specification violation: the parser no longer accepts `char[]` as a return type. Shalimar 3.0 explicitly prohibits *all* array returns; callers pass an array by reference instead. The separate user-approved `fun main()` shorthand remains accepted as an amendment to the uploaded grammar.

This is an **audit and first correctness fix**, NOT completion of P0/P1/P2/P3 native backends. Do not label any unsupported backend as passing. The test runner records gaps as `GAP`, and a failed semantic expectation as `FAIL` (exit code 1).

## Verified on the current Linux build host

- 12/12 normative example programs: frontend `--check` PASS.
- 11/11 targeted negative tests: correctly rejected (including the newly fixed `char[]` output).
- 0/24 normative example native Windows COFF objects: currently supported. All 24 Debug/Release probes record GAP.
- CodeView/PDB: GAP; the compiler correctly refuses to claim support.
- Linux x86-64 ELF: GAP; target selection/native ELF emission not integrated.
- macOS ARM64 Mach-O: GAP; target selection/native Mach-O emission not integrated.
- TI TMS6747: GAP; target selection/native DSP emission not integrated.
- Compiler source allocation-token scan: PASS for explicit `new`, `delete`, `malloc`, `free` tokens. This is a lightweight scan, **not** a proof of memory safety or absence of all pointer usage.
- Existing rev44 XMM, rev45 native sqrt, rev46 native Windows linking, rev47 Windows runtime *build gate*, and rev48 debug-map regression scripts: PASS. The rev47 gate does **not** run the DLL on Windows.

The exact machine-readable results are in `tests/conformance/rev49_results.json` and are regenerated by:


## Open work ordered by requested target priorities

### P0 — Windows x86-64 COFF/CodeView/PDB

General typed IR-to-native lowering (integer/real/char expressions, locals/globals, control-flow, loops, functions, references, multi-results), arrays and strings, `?`/`??`/`prec`, full `uses` catalogue, native diagnostics, executable linkage to real runtime, actual Windows execution, CodeView/PDB, source stepping, and Debug/Release equivalence. Current limited native `sqrt` and COFF linking are foundational only.

### P1 — Linux x86-64 ELF/DWARF

Integrate native S-IR lowering and ELF object emission, ABI, relocations, runtime linking, DWARF source and variable locations, execution and regression tests. A legacy C++98-ported emitter exists but is not proof of complete S-native integration.

### P2 — macOS ARM64 Mach-O/DWARF

Integrate native S-IR lowering and AArch64 code generation, Mach-O object/relocation writer, Darwin ABI, runtime linking, DWARF, Xcode 26+ project validation, and execution tests on an actual macOS host.

### P3 — TI TMS6747 DSP

Complete DSP instruction selection, calling convention, object/linker contract, runtime model, hardware/simulator execution tests, and target-specific Debug/Release acceptance. A target contract and legacy emitter do not constitute end-to-end support.

## Additional specification risks

- The uploaded document describes the original Swift interpreter and app/editor implementation notes; those notes are *not* evidence that the C++ compiler implements equivalent behavior.
- String return behavior in older compiler tests conflicts with normative 3.0; those tests need to be reclassified as expected rejection rather than used to re-enable a prohibited language feature.
- Cross-file imports described by `CROSSFILE.md` and foreign-function candidates in `FOREIGN.md` require separate validation; those referenced documents were not supplied with the uploaded normative file.
- The original spec examples' historic `run-spec-examples.sh` emits C and is obsolete for S-native-only builds. Use the new native conformance runner, which never invokes a C backend.
- 12/12 `--check` is a structural/semantic acceptance result, **not** runtime correctness, and the negative cases are an initial suite rather than full coverage of the 1393-line specification.

## Release rule

A target may be marked complete only after positive native object and link tests, actual target execution, correct results and diagnostics, verified Debug symbols and Release equivalence. Never promote a `GAP` to `PASS` based solely on architecture files or successful compilation.
